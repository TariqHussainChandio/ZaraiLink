# P1: quality gates and how each was proven (2026-09-21)

Phase P1 turns the project's rules into checks that fail by themselves. Every gate below was proven **locally**,
by planting a violation in a throwaway copy and confirming the gate rejects it, then confirming the real tree
passes. The one thing that cannot be proven without you is the same check running on **GitHub**, because that
needs a push. [`scripts/ci/plant-violations.sh`](../../scripts/ci/plant-violations.sh) plants one violation per
gate so that final proof takes a few minutes.

## The gates

| Gate | Blocks | Runs in | Proven by (locally) |
|---|---|---|---|
| **Reality gate**, strict rules | Stubs, "not implemented", TODO without an issue, empty catch blocks, type-check suppressions, test doubles or `print()` in production code | CI `reality`, git hook | 30 tests in [`scripts/test_check_reality.py`](../../scripts/test_check_reality.py); each plants a violation in a throwaway repo and asserts it is rejected |
| **Reality gate**, ratchets | `as any`, `console.*`, empty handlers, lint suppressions, broad `except` rising in any file; a new file starts at zero | CI `reality`, git hook | Same test file: growth in one file, a new file, and "fix one file, break another" are all rejected |
| **ruff, ruff format, mypy** ratchets | Any new lint, formatting, or type finding in any backend file | CI `backend` | Same test file plants an unused import and a type error |
| **knip and ESLint** ratchets | New dead code or ESLint warnings in any file | CI `frontend` | A throwaway repo with the real ESLint config: a planted unlimited `eslint-disable` and an orphan file are both rejected |
| **Commit message lint** | Messages that are not Conventional Commits | git hook, CI `pr-hygiene` | Throwaway repo with the hooks installed: `update stuff` is rejected, `feat(test): add ok` is accepted |
| **Secret scan** (gitleaks) | Any secret in a commit; full history scanned in CI | git hook, CI `security` | A planted GitHub token is rejected in the hook; the real history (15 commits) and 210 new or changed files scan clean |
| **Dependency audit** (OSV-Scanner) | Any known vulnerability not listed in [`osv-scanner.toml`](../../osv-scanner.toml); each accepted entry expires | CI `security` | Removing the torch entry makes it fail (2 Critical, 16 High); with the entries it passes |
| **Static analysis** (Semgrep) | OWASP Top 10, TypeScript, and Python rule violations | CI `sast` | A planted `subprocess(shell=True)` is rejected; the real code has zero findings |
| **Workflow lint** (actionlint, zizmor) | Script injection, unpinned actions, excessive permissions, dangerous triggers | CI `workflow-lint` | A planted insecure workflow is rejected by both; `ci.yml` passes both (zizmor online) |
| **Real-stack tests** | Any migration that does not apply; the two known defects being fixed without their marker being removed | CI `database` | The job's exact steps were run locally: the schema lints clean and the admin-signup test fails as expected against real Auth |
| **Aggregate** `ci-required` | A failed or cancelled job; skipped jobs are fine | CI | Logic reviewed only; cannot be proven without GitHub |

Every job has an explicit token permission, a timeout, and every third-party action is pinned to a commit SHA.
Downloaded tools are pinned to a SHA-256 kept in the repository ([`scripts/ci/install-tool.sh`](../../scripts/ci/install-tool.sh)).

Coverage is reported on every run and not enforced yet: frontend about 89% statements and 75% branches,

## What the new tools found that the old checks could not

- **mypy reports 25 attribute errors: the same 25 write paths that crash at runtime** ([baseline N1](baseline-2026-09.md)).
  A type check alone would have caught the defect that 124 mocked tests hid.
- **OSV-Scanner reports about 100 advisories in 11 pinned versions** (Pillow, Starlette, torch, python-dotenv,
  pytest, and five transitive npm tools). Torch alone has 2 Critical, including the model-loading remote-code
  execution. The upgrade phases remove them, and the expiry dates force it.
- **Frontend lint has 17 real warnings** (16 unstable nested components in the navigators) that were never surfaced.
- **ESLint was linting generated coverage reports.** Fixed with `.eslintignore`.
- **`react-native-svg` is not unused**, contrary to earlier notes: the icon library needs it. The plan no longer
  proposes removing it.
- **A CI defect caught before it shipped:** the bare `pytest` command could not import the app (only
  `python -m pytest` could), so the first run of the new backend job would have failed. Fixed in `pyproject.toml`.

## Deviations from the plan

| Plan said | What I did | Why |
|---|---|---|
| One deliberate-failure pull request per gate | Proved every gate locally, and prepared one script that plants all of them | Pushing and opening PRs needs your commits; the proof on GitHub is the remaining step |
| Gradle cache in CI | Deferred to phase P2 | The Android job is rebuilt when the project moves to Expo |
| `pip-audit` | OSV-Scanner only | It reads both lockfiles, audits the CPU torch build that `pip-audit` cannot, and supports expiring exceptions |
| Hooks opt-in | Hooks install automatically on `npm ci` | That is lefthook's standard behaviour; skip one commit with `LEFTHOOK=0` |
| `requirements.txt` | Removed; `pyproject.toml` and `uv.lock` replace it | Two sources of truth would drift |

## Not proven, and needs you

1. **The pipeline on GitHub.** After committing, run the planting script on a throwaway branch and open a draft PR
   with a non-conventional title (see the header of `plant-violations.sh`). Every named job must fail for the
   planted reason and `ci-required` must be red. Then delete the branch.
2. **First-run surprises are possible** in jobs that can only run on GitHub: the Semgrep and `uvx` steps, and the
   Supabase CLI action. Fix what the first run shows.
3. **Branch protection** cannot be turned on until the repository is public (phase P3), so until then the pipeline
   informs rather than enforces.

## An incident during this phase

While setting up a throwaway repository to test the hooks, a failed `git clone` left my command running in **your
real repository**. It installed the two lefthook hooks and set a test git identity ("Hook Test") in your local git
config. I found it in the next check and reverted both: the hooks are removed, the identity is back to yours, and
`.git/config` matches its original contents. The cause was not verifying the working directory before running
state-changing commands; every later test used a scratch directory guarded by a path check, and `AGENTS.md` now
forbids touching git configuration or hooks in your repository.
